## 1. 研究目标与预期交付

在 ALFWorld 中，智能体失败后会重置环境并重试。文字反思只有在正确理解上次经历、并促成下次有效行动时，才可能提高成功率。本项目回答：**固定模型、动作策略和重试预算，只改变失败后的反思提示词，能否提高三次尝试内的任务成功率，增加或节省多少成本？**

具体动机来自已有 CD 任务：环境已确认拿到 CD，B 的反思却说没有找到。这提示我们检查“观察事实 → 反思内容 → 重试行动 → 任务结果”之间哪里出了问题。正确描述上次拿到物品，也不代表重置后仍持有它；反思需要把可复用的经验与已清空的环境状态区分开。

最终交付一套可复现的课程 A/B/C 实现、30 题留出评测、配对结果图与成本表，以及有原始轨迹支撑的案例分析。首先完成可信的对照和解释；C 提升、持平或退步都如实交付。开发阶段验证有用的提示词才推荐进入最终版本；若没有稳定收益，选一个合规、可解释的 C 完成课程比较，明确其收益尚未成立。

**已确认的协作方式：**你批准研究方向和本轮 GPU 预算；AI 在该范围内查资料、试提示词变体、跑开发集并逐步报告。换方向、追加预算、冻结 C 由你决定。最终只做课程框架，C 只改反思提示词。这两项沿用[关联聊天中的明确选择](codex://threads/01a203c3-1cc2-7cf3-9f50-89367af9f85f)。

## 3. 研究假设：一次回答一个问题

Reflexion 的原始反思指令已经要求简洁、具体的新行动计划。因此，本项目检验的是更明确的提示约束在当前模型与任务中的效果，尚无证据支持新算法或普遍改进的论断。B 的完整实现与版本见[固定上游反思函数](https://github.com/noahshinn/reflexion/blob/218cf0ef1df84b05ce379dd4a8e47f17766733a0/alfworld_runs/generate_reflections.py)。

| 候选 | 可检验假设与唯一改动 | 最小比较 | 竞争解释与否定信号 |
| --- | --- | --- | --- |
| **C01：反思依据观察**，推荐优先 | 在 B 的英文反思指令中增加一项要求：用观察支持对失败与已确认进度的判断，区分上次事实与重置后需重做的动作。预计减少事实矛盾，并可能改善恢复 | B 与 C01；同一开发清单、模型、种子和反思输入 | 文本可能更准确，但小模型仍不会执行；若事实矛盾减少而成功数不增，只保留局部质量发现 |
| **C02：一个具体纠错动作**，待选 | 在 B 的英文反思指令中增加一项要求：聚焦一个下一次可执行的纠错动作。预计减少重复与输出到限，并可能改善恢复 | B 与 C02；保持 256 token 上限，不叠加 C01 | 单个动作可能漏掉多步依赖；输出变短、成功数下降则不推荐；只降成本则单列效率发现 |
| **C01+C02：组合**，条件性 | 两个单项都完成复核后，检验组合是否优于最佳单项 | 同条件比较 B、C01、C02、组合 | 两项可能重复或相互干扰；组合无额外收益时保留更简单的单项 |

每个获批方向默认最多试两版提示词，均记录全文和结果；扩大候选数量作为新的研究决定提交。第一版从上述最小改动开始，第二版只能针对第一版已观察到的问题调整。两版均无收益，则关闭该方向并简记原因。新论文只用于提出候选，外部成绩不写成本项目收益。

先标注现有 B 的全部 10 条反思，记录：事实是否与观察一致、建议是否可执行、是否混淆重置前后状态、下次是否出现对应行动、最终是否成功。CD 是问题例，放书是“成功未必由正确反思带来”的反例。后续沿用同一标注口径，不因 C 的输出改变标准；由另一人或另一工作线复核分歧。轨迹支持行为解释，不足以证明模型内部推理。

2026-11-23 补充：[五类错误表](../experiments/reflection-error-taxonomy.md)统一事实、归因、更新、剩余目标和信息密度的口径；[文献与方案](../papers/reflection-remedies-2026-11-23.md)列出 S1–S5，供重新评估具体改法。其中 S1 承接 C01，其余属于待选候选，不自动变成已获批方向或增加提示词试验额度。当前先审阅分析与方案，不推进 GPU 试跑。

## 4. 比较条件与指标

| 项目 | 固定设计 |
| --- | --- |
| A / B / C | A 重试无反思；B 使用原始 Reflexion；C 只替换英文反思指令，其余与 B 相同 |
| 模型与环境 | 沿用 `configs/baseline.json` 的 Qwen2.5-1.5B-Instruct Q4_K_M、llama.cpp b12244、ALFWorld 0.4.2、TextWorld 1.6.2；运行前核对 revision 与哈希 |
| 输入与动作 | 共用动作提示、两份原始示例、轨迹及原记忆机制；C 不增加检索、工具、模型调用、人工答案或程序化记忆改写 |
| 预算与停止 | 每题最多 3 次尝试，每次最多 30 个环境动作、49 个策略回合；动作输出上限 128、反思 256、上下文 8192 token；成功即停 |
| 解码与重置 | 保持原采样参数及种子公式；每次恢复同一任务初始状态并核对哈希；失败且还有重试时才生成反思 |
| 数据 | `configs/task_registry.json` 固定 10 道 `valid_seen` 开发题、30 道 `valid_unseen` 留出题，ID 交集为零；只用开发集选择 C |
| 配对与复核 | 建议开发种子 4051、复核种子 4052，在首次新结果前登记；每个种子内 B/C 配对，首次动作输入及种子一致；随机性与硬件差异照实记录 |

**主指标：**每组在三次内成功的任务数，以及 C 减 B 的配对绝对差。开发集分母 10，留出集分母 30；同时报告“仅 C 成功”和“仅 B 成功”，不把重试或步骤当新样本。

**辅助指标：**首次成功率；首败后恢复率的实际分子/分母（分母为零时记不适用）；环境动作、模型调用、输入/输出 token、反思到限比例、后端推理秒和实际 GPU 卡时。反思质量及行动改变作为解释性指标。推理秒与计费卡时分别报告，成本包含生成反思；设备或负载不一致时不把耗时差解释为方法的因果收益。

相同开发题换种子只检验运行波动，不算独立任务确认。留出题包含场景分布变化，开发成绩不能直接外推。正式报告如做区间估计，按任务保持组间配对；共享任务模板/场景的相关性需说明，多种子与多次尝试不增加独立任务数。完整计划中的未执行、技术中断和环境失败单列，保留预定分母，不删除不利任务或将中断当正常失败。

## 6. 什么时候继续、淘汰或纳入最终版本

| 观察结果 | 判断与下一步 |
| --- | --- |
| 十题净多成功至少 1 题，比较条件与日志完整 | 进入另一组预登记种子的复核；这是探索筛选门槛，不表示统计显著 |
| 同一冻结候选在两个登记种子上均比各自 B 净多成功至少 1 题 | 有开发集稳定收益的候选；结合退步题、轨迹及实际成本向你推荐冻结，不称普遍有效 |
| 只改善反思准确性，或只减少 token，成功数持平 | 分别记录质量或效率发现；不升级为成功率提升，是否保留由你按代价权衡 |
| 复测打平/退步，或两版均无增量 | 标记未见稳定收益，主计划留一行结论和报告链接，不继续刷版本 |
| 组合未超过最佳单项 | 保留更简单、成本更低的单项，不因包含更多规则而保留组合 |
| 提示词未注入、重置错误、任务/版本不一致或运行中断 | 记工程失败/部分完成，修复后用新 run ID；此前结果不用于判断假设，费用与日志保留 |
| 所有候选均无稳定收益 | 提交最小、合规、可解释的 C 供你冻结，完成正式比较并报告负结果；不改模型或查看留出集寻找提升 |

候选在复核前锁定；复核后再改文本即成为新版本，既有复核不能转移。若复核无预算，写“待复核”。数据出分后不改门槛。论文/资料检索允许提出新方向，但运行新的方向须由你选择。

## 7. 多工作线、预算与反馈

**分工。**协调工作线维护本计划的状态表、预算和 GPU 队列；文献工作线负责出处、最近方法差异及可迁移的一句提示词；实验工作线负责代码和运行；复核工作线从原始日志重算结果。各工作线只修改自己的文件，协调者核对产物后汇总。人员和 AI 会话可以按资源兼任，但关键结果不能只有实验者自评。

每个获批方向使用独立本地分支/worktree，例如 `research/c01-observation`、`research/c02-next-action`。公共 C 支持放在 `feat/course-c-runner`，A/B 回归合格后作为方向分支的同一起点；`integration/course-final` 只接收你选定的最终实现。当前检出为 `exp/anchor-attempt-1`，基线可从 `feat/alfworld-baseline` 查起，文档有未提交修改。实施时核实基准 SHA，不能把当前 Anchor 策略带入课程对照；保存未提交文档，单独核对 worktree 中被忽略的数据、模型和日志路径。Git 提交、推送与正式合并沿用既有权限，本次未执行。

文献、轨迹分析和复核可并行，单 GPU 模型任务串行；同一设备、可比负载下比较耗时。方向报告各自独占，协调者独占主计划。获批范围内的常规步骤连续推进，不逐条请求许可；遇到阻塞转做其他已批准工作，留下明确恢复点。

**预算。**项目总上限沿用 **30 GPU 小时**，当前累计消耗与学校余额尚未核实，不能默认还剩 30 小时。每轮先记录：总上限、历史已用、当前在跑/预留、正式评测预留、本轮批准可用。实际卡时按分配时长 × 卡数计，后台空闲占用和失败运行也登记；本地 GPU 与学校账目分列，并说明是否计入课程额度。

先用已批准的短运行在目标硬件测卡时，估算完整正式评测及必要复核，再分配探索预算；后端推理秒不能代替卡时估算。本轮上限不足、正式预留不足或账目无法确认时，暂停新增 GPU 作业并报告，继续已有日志分析。压缩顺序为组合实验 → 次要方向 → 额外种子；仍无法完成正式核心比较时，将具体缺口交你决定，不自行删题或加额度。

**逐步报告。**每完成文献筛选、轨迹标注、工程验收、试跑、十题比较、复核或冻结，都交一份短报告。进行中的研究每个北京时间自然日至少汇总一次；会话结束前写恢复点。不承诺会话结束后自动后台运行，定时执行需另外配置。出现阻塞、预算风险或关键反证时及时报告。

报告放在 `docs/reports/<方向>-<序号>-<步骤>.md`，建议正文约一屏，附表和轨迹另存并链接：

| 字段 | 必须回答 |
| --- | --- |
| 结论 | 保留、淘汰、复核或待决定；一句话给关键数字 |
| 问题与比较 | 假设、唯一变化、任务清单、种子、对照与候选版本；实验前填写并留存，出分后追加结果 |
| 实证 | 实验给逐题配对表/图、分子分母与成本；文献给原文和适用性；工程检查给命令及实际输出；不编造缺失图表 |
| 分析 | 改善题与退步题、至少一个竞争解释、观察支持到哪一层 |
| 复现与下一步 | SHA 或可重放补丁、配置/提示词哈希、run ID、日志、卡时、下一动作及需你决定的选项 |

报告优先解释“为什么值得做下一步”。主计划只留下当前决定、关键数值和报告链接；无明显效果的方法一行归档，全部候选和失败证据仍保留。原始日志不覆盖，技术重跑有新编号和原因。已授权的共享平台更新要回读验证，未同步则在本地交接中注明。

## 9. 写法来源与版本记录

本计划采用此前比较过的四种写法，各解决一个具体问题：

- [Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/main/0000-template.md)：先说明动机和具体案例，再讨论方案、替代解释与局限，对应第 1–3 节。

- [Stanford CS348K 项目指南](https://github.com/stanford-cs348k/project/blob/master/README.md)：从最终图表与交付物倒推工作，优先打通最小端到端流程，对应第 1、5 节。
